Central source of truth

Device State Engine + Issue Rule Engine

เอกสารนี้เป็นแผนกลางสำหรับตอนลง code จริง: ข้อมูลจาก MQTT, Node-RED, Provider API, Django Ninja, Channels หรือ future InfluxDB ต้องถูกรวมและตัดสินสถานะที่ backend จุดเดียว ก่อนส่งให้ UI ทุกหน้าแสดงผล.

Core rule

UI never decides device health.

Dashboard, Map, Device List, Faults, Notifications และ Audit Logs ต้อง render จาก normalized state + active issue เดียวกันเท่านั้น.

UI มี 2 mode หลัก: Portfolio UI สำหรับ Platform Owner/Dealer และ Customer UI สำหรับ site operation. ทั้งสอง mode ใช้ state engine เดียวกัน ต่างกันเฉพาะ scope/filter/card visibility.

Architecture

6-layer implementation flow

Normalize -> State -> Issue -> API -> UI
1Ingestion

รับ raw telemetry, command ACK, provider event, manual import, Node-RED payload โดยยังไม่ตัดสินว่า OK หรือ fault.

2Normalize

แปลงข้อมูลเป็น normalized event ที่ field/หน่วย/เวลา/source ตรงกัน.

3Device State Engine

คำนวณ latest state: online, command, lamp, electrical, overall, severity.

4Issue Rule Engine

ตรวจ rule เช่น lamp_state_unconfirmed after debounce, command timeout, voltage sag แล้วสร้าง/อัปเดต issue.

5Read Model + API

เก็บ latest state, active issue, event timeline แล้ว expose ผ่าน API กลาง.

6UI Renderer

ทุกหน้าอ่าน state เดียวกันและแสดงตาม role/package/scope.

Implementation rule

Package ไม่ควรแปลว่า device ส่งข้อมูลเท่าไรก็เขียน raw ลงฐานทั้งหมดเสมอ. Package คือ policy ว่าเราคาดหวัง/คิดค่าบริการ/แสดงผล/เก็บละเอียดแค่ไหน ส่วน ingest pipeline ต้องรองรับ over-sampling, late event, duplicate event และ downsampling.

Rules

Issue detection rules ที่ต้องทำก่อน UI

Backend-owned logic
Electrical P1/P2LAMP_STATE_UNCONFIRMED

Provider accepted ON/OFF command แต่ verification_status เป็น state-not-yet-confirmed หรือ snapshot มี has_unpowered_evidence ต่อเนื่องเกิน debounce window. แสดงเป็น active issue หลังพ้น pending window เท่านั้น.

Electrical warningLOW_CURRENT_WHILE_ON

Command ON แต่ current ต่ำกว่า threshold ตาม device model/spec. ยังไม่ฟันธงว่าดับ แต่อยู่ใน issue queue.

CommandCOMMAND_TIMEOUT

ส่ง command แล้ว provider/runtime ไม่ยอมรับ หรือไม่มี ACK ภายใน timeout. เป็นคนละปัญหากับ state-not-yet-confirmed เพราะกรณีนั้น provider รับคำสั่งแล้วแต่ telemetry ยังไม่ยืนยัน.

ConnectionOFFLINE_OVER_THRESHOLD

ไม่มี telemetry เกิน threshold. ต้องขึ้น map marker, dashboard issue, notification และ device-list row.

Power qualityVOLTAGE_SAG / OVER_VOLTAGE

แรงดันผิดช่วงตาม threshold/site policy. ใช้ใน Electrical Health, heatmap, graph marker, faults.

PerformancePOWER_SPIKE / POWER_DROP / POOR_PF

ใช้ตรวจ anomaly, maintenance risk, expected vs actual watt และ zone load imbalance.

Critical tests

ON accepted + state-not-yet-confirmed past debounce -> LAMP_STATE_UNCONFIRMED
ON + no ACK -> COMMAND_TIMEOUT
No telemetry -> OFFLINE_OVER_THRESHOLD
Voltage low -> VOLTAGE_SAG
Repair closed + telemetry normal -> issue resolved
Package expired -> ingest continues but UI/actions locked
