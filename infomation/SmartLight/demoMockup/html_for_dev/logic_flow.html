Architecture Decision

เพิ่ม InfluxDB ได้ แต่ต้องไม่ทำให้ flow ชนกับ Django Ninja และ Channels

เอกสารนี้อธิบาย flow ที่เหมาะกับ SmartLight ปัจจุบัน: MQTT/EMQX, Node-RED, Django Ninja, Django Channels, Celery, PostgreSQL, InfluxDB และ MCP/AI โดยแยกหน้าที่ให้ชัดว่าอะไรเป็น source of truth, อะไรเป็น telemetry store, และอะไรเป็น realtime transport.

Recommended Decision

ใช้ backend เป็น ingestion authority

Node-RED ต่อ MQTT ได้ แต่ข้อมูลควรเข้าผ่าน Django Ninja ingestion API หรือ Python MQTT consumer ที่ใช้ service logic เดียวกัน แล้ว backend ค่อยเขียน PostgreSQL, InfluxDB และ broadcast ผ่าน Channels.

Executive Summary

ข้อสรุปหลัก

Source of TruthPostgreSQL

business data, account scope, latest state, command, fault, ticket

Time-Series StoreInfluxDB

raw telemetry, graph history, trend, anomaly, downsample

Realtime UIChannels

Recommended core flow:
Device -> MQTT/EMQX -> ingestion layer -> Django service logic
                                  |-> PostgreSQL latest/business/fault
                                  |-> InfluxDB telemetry history
                                  |-> Celery async processing
                                  |-> Django Channels realtime broadcast
Current State

ระบบเรามีอะไรอยู่แล้ว

จาก codebase ปัจจุบัน ระบบไม่ได้เริ่มจากศูนย์ เรามี backend surface และ realtime infrastructure แล้ว ดังนั้น InfluxDB ควรเพิ่มเข้ามาเป็น storage layer ไม่ใช่เปลี่ยน architecture ทั้งหมด.

Django Ninja API

มี runtime/device/dashboard/API integration endpoints อยู่แล้ว ใช้เป็น contract กลางสำหรับ query, command, ingestion และ MCP tool ได้.

Django Channels

มี WebSocket consumers สำหรับ device/fault/notification และ account-scoped group อยู่แล้ว ใช้ broadcast realtime event ไป frontend.

Celery + Redis

มี task infrastructure อยู่แล้ว เหมาะกับ retry, async fault evaluation, summary rollup, notification และ health checks.

PostgreSQL

มี device, command, device reading, fault, account, package, zone/tag models อยู่แล้ว เหมาะเป็น business source of truth.

Node-RED

มี integration guide และ docker service อยู่แล้ว เหมาะเป็น bridge/test/simulator แต่ไม่ควรเป็นสมองหลักของ fault/business rules.

MQTT / EMQX

เป็น broker สำหรับ telemetry/status/command topic ได้ แต่ broker ไม่ควรตัดสิน business logic เอง.

Target Flow

flow ที่แนะนำสำหรับ production-ready architecture

1. Device

ส่ง telemetry/status ผ่าน MQTT และรับ command ผ่าน topic ที่กำหนด.

2. EMQX

broker เท่านั้น ทำ routing/topic/auth ไม่ตัดสิน business logic.

3. Ingestion

Node-RED bridge หรือ Python MQTT consumer รับ payload แล้วเรียก service logic กลาง.

4. Django Service

validate schema, resolve device/account, normalize metric, dedupe, rule entrypoint.

5. Storage

PostgreSQL สำหรับ state/business, InfluxDB สำหรับ telemetry history.

6. Realtime

Channels broadcast เฉพาะ event ที่ผ่าน backend แล้ว.

MQTT telemetry -> ingestion service -> normalize/validate
normalize/validate -> PostgreSQL latest state + fault/event
normalize/validate -> InfluxDB raw telemetry point
PostgreSQL update/fault -> Channels group_send(account/device/fault)
heavy work -> Celery task -> summary/notification/anomaly follow-up

Fault Logic

ตัวอย่าง logic: สั่ง ON แล้วไฟไม่ติด หรือกระแสตก

Fault logic ไม่ควรอยู่กระจัดกระจายใน Node-RED, InfluxDB และ frontend พร้อมกัน จุดตัดสินควรเป็น backend service เดียว เพื่อให้ audit, permission, retry และ test ได้.

1

ส่ง command

ผู้ใช้กด ON/OFF/DIM ผ่าน frontend หรือ API. Django Ninja เรียก command service แล้วสร้าง DeviceCommand ใน PostgreSQL พร้อม correlation id/source/user.

2

ส่งไป provider/MQTT

backend dispatch command ไป provider หรือ MQTT topic. สถานะ command เป็น sent/pending ตาม response.

3

รอ telemetry feedback

device ส่ง telemetry กลับมาทาง MQTT เช่น lamp_state, current_a, power_w, voltage, brightness, rssi.

4

ingestion ตรวจเงื่อนไข

backend service เปรียบเทียบ expected state กับ actual telemetry เช่น command ON แต่ current_a = 0 หรือ power_w ต่ำกว่า threshold ภายในเวลา X วินาที.

5

สร้าง fault/event

ถ้าผิดเงื่อนไข สร้าง FaultOccurrence/AlertEvent ใน PostgreSQL และผูกกับ command/device/account.

6

broadcast และ notify

Channels ส่ง event ไป dashboard/device-list/map. Celery ทำ notification, retry, escalation หรือ summary ตาม rule.

Ninja + Channels Design

ใช้ Django Ninja และ Channels อย่างไรไม่ให้ชนกัน

Django Ninja = request/command/query/ingestion

  • รับข้อมูลจาก Node-RED หรือ external ingestion
  • frontend เรียก dashboard/device/map data
  • MCP/AI เรียก tool/API ที่ enforce permission
  • command write ทุกทางต้องผ่าน service กลาง

Django Channels = event push เท่านั้น

  • ส่ง device_update หลัง update database แล้ว
  • ส่ง fault_detected หลัง backend สร้าง fault แล้ว
  • ส่ง command_result หลัง command service ตัดสินแล้ว
  • ไม่รับ raw MQTT เป็น business ingestion หลัก
Correct:
POST /api/v1/ingestion/telemetry -> service -> DB/Influx -> Channels group_send

Avoid:
MQTT raw -> Channels -> frontend decides fault
MQTT raw -> InfluxDB -> PostgreSQL business state
Node-RED Options

มี 2 ทางเลือก แต่ควรเริ่มแบบ pragmatic

Phase 1 Recommended

Node-RED เป็น MQTT bridge

เหมาะกับช่วงแรก เพราะเร็ว เห็น flow ชัด และเราใช้ Node-RED อยู่แล้ว.

  • MQTT in node subscribe telemetry topic
  • function node normalize payload เบื้องต้น
  • HTTP request POST เข้า Django Ninja ingestion API
  • ไม่เขียน PostgreSQL/InfluxDB โดยตรงถ้าไม่จำเป็น
Production Target

Python MQTT consumer service

เหมาะระยะยาว เพราะ test, deploy, retry, validation และ tenant security คุมได้ดีกว่า.

  • ใช้ service logic เดียวกับ ingestion API
  • รองรับ idempotency/dedupe
  • รองรับ structured logging
  • ลด dependency ที่ business logic ไปอยู่ใน Node-RED
MCP / AI

MCP/AI ควรเรียกข้อมูลผ่าน backend boundary

AI ไม่ควรถูกปล่อยให้ query raw PostgreSQL และ InfluxDB โดยตรงแบบไม่มี account scope เพราะระบบเป็น multi-tenant. ควรทำ MCP tools หรือ API ที่ backend รวมข้อมูลให้แล้ว.

MCP Tool

เช่น get_device_health, get_fault_timeline, get_energy_summary.

Backend API/Service

validate requester, account scope, device visibility, package capability, query policy.

PostgreSQL + InfluxDB

PostgreSQL ให้ context/business/fault, InfluxDB ให้ historical telemetry.

Recommended MCP tools:
- get_device_health(device_id, account_scope)
- get_customer_energy_summary(account_id, period)
- get_fault_timeline(device_id, period)
- explain_command_failure(command_id)
- recommend_maintenance_action(device_id)
Anti Patterns

สิ่งที่ไม่ควรทำ

MQTT -> InfluxDB -> PostgreSQL

ผิดบทบาท เพราะ InfluxDB ไม่ควรเป็น source of truth สำหรับ business state/fault/permission.

Node-RED เขียนทุก DB เอง

debug ยาก, test ยาก, logic กระจาย และเสี่ยง bypass account/tenant rules.

Frontend ตัดสิน fault เอง

ผู้ใช้แต่ละเครื่องเห็นไม่เท่ากัน และไม่มี audit/event lifecycle.

Channels รับ raw telemetry โดยตรง

Channels ควรเป็น realtime delivery หลัง state ถูก validate แล้ว ไม่ใช่ ingestion engine.

เก็บ raw telemetry ทั้งหมดใน PostgreSQL

ถ้าข้อมูลถี่มาก dashboard/history จะหนักและ retention จัดการยาก.

AI query database ตรง

เสี่ยง multi-tenant leak และ business rule ไม่ถูก enforce.

Final Decision

คำตอบสุดท้ายของ architecture นี้

เพิ่ม InfluxDB ควรทำ แต่ต้องเพิ่มเป็น telemetry time-series store ใต้ backend ingestion layer ไม่ใช่ให้ InfluxDB หรือ Node-RED เป็นตัวคุม business logic หลัก.

Django Ninja = API + ingestion boundary PostgreSQL = business source of truth InfluxDB = raw telemetry/time-series Channels = realtime push Node-RED = bridge/test first Do not bypass backend rules 
Best target:
MQTT/EMQX -> backend-controlled ingestion -> PostgreSQL + InfluxDB -> Channels/Celery/API/MCP

Pragmatic first step:
MQTT/EMQX -> Node-RED bridge -> Django Ninja ingestion API -> PostgreSQL + InfluxDB -> Channels

เอกสารนี้เป็น architecture plan สำหรับตัดสินใจต่อ ไม่ได้แก้ production settings, docker-compose หรือ API implementation.
