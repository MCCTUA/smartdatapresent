Layout Roadmap First · 2026-06-08

เริ่มรอบถัดไปด้วยการล็อก roadmap layout ให้ครบก่อนลง logic เพิ่ม. เป้าหมายคือรู้ว่าแต่ละหน้าใช้ mock/spec ไหน, production route/template ไหนต้องแก้, section ไหนมีหน้าที่อะไร, และ logic ควรอยู่จุดกลางใด เพื่อไม่แก้เรื่องเดียวกันหลายจุด.

Layout Rules

  • Dashboard: production layout ใน templates/core/dashboard.html เป็นตัวหลัก แต่ต้องใช้ shared header include เสมอ. คง KPI production set เดิม แล้วเติมเฉพาะ graph/layout contract จาก docs/html/dashboard.html โดยไม่ copy mock values.
  • Protected dashboard KPI set: ต้องคงกลุ่ม Management, Operations, and Risk KPIs. Management = Current / Total Usage, Energy Saving, Energy Change. Operations = Connectivity, Telemetry Quality, Lamp Health, Maintenance Active. Risk = Thermal Risk, Unexpected Power, Lamp State Issue.
  • Other pages: ใช้ docs/html/*.html เป็น layout reference แล้วนำโครง section/class vocabulary เข้าหน้า production เท่าที่ route, permission, theme token, และ backend data อนุญาต.
  • Theme: ใช้โทนสี production เดิมจาก shared shell/white-label variables. ห้ามยกสี docs/mock มาครอบ production.
  • Data: ห้ามใส่ fake rows, mock counters, หรือ future-only action ใน production. ถ้ายังไม่มี data source ให้ทำ empty/locked/pending state ที่มาจาก backend context.
  • Remarks: ระหว่างแก้ layout ให้ใส่ comment/marker แบบไม่แสดงบนจอ ระบุ purpose ของหน้า/section, docs source, production route/template/view, data owner, และ logic owner.
  • Logic boundary: template มีหน้าที่ view เท่านั้น. Logic ที่ซ้ำหรือเกี่ยวกับ scope, permission, package, device state, report/export, notification/work-order, audit/compliance ต้องย้ายไป service/helper/policy กลางพร้อม test.

  • Layout source: mock/spec file และ section ที่อ้างอิง.
  • Production owner: route name, template, view/service, CSS/JS file ที่เกี่ยวข้อง.
  • Data contract: context keys/API/service ที่เติมตัวเลข, table rows, badges, drawer, filters, actions.
  • Logic owner: service/helper/policy ที่ต้องเป็นจุดกลาง ถ้าหน้านี้ต้องคำนวณ scope, entitlement, state, report, command, audit, หรือ notification/work-order workflow.
  • Status: layout-locked, needs-layout-pass, blocked-by-missing-data, หรือ logic-later.

Pre-Code Layout Analysis Standard

  1. Inventory mock features first: Read the mock UI and list its features as neutral candidates, such as summary counts, filters, map previews, report/export actions, tables, drawers, package states, and command actions. These examples are not rules; each menu must be reasoned about independently.
  2. Read the menu name next: The sidebar/menu label defines the page responsibility. Example: /backoffice/ is Admin Management, so analytics/report previews were removed.
  3. Map the page shape: Write page -> section -> card/control/table -> route/menu/data source before editing templates.
  4. Compare mock vs production route: Keep only the mock features that match the production route contract. Move or remove features that belong to another route.
  5. Look for missing menu-owned features: The mock is only one input. If the menu responsibility implies a needed feature that the mock does not show, add it to the analysis as an add candidate before coding.
  6. Compare against completed patterns: Reuse shared header/top back navigation, single-frame filters, section purpose markers, scoped backend context, and route CSS modifiers from the completed pages above.
  7. Classify each feature: Mark every candidate as keep, add, remove, move, or duplicate allowed. The reason must reference the menu responsibility and the backend owner, not only visual preference.
  8. Classify duplication: Duplicate data is allowed only when the same feature has a different role in that menu. Example: lamp totals may support monitoring on Dashboard, marker context on Map, report scope on Reports, and readiness on Admin Management. Remove duplicates that only repeat sidebar/menu links or route-owned detail tables.
  9. Identify logic owner: Every visible section must name its view/service/form/context owner. If no backend owner exists, mark the section layout-ready only or leave it out.
  10. Patch narrowly: Implement only the chosen route. Do not move mock numbers, mock rows, or docs-only JavaScript into production.
  11. Delete proven-unused code: When a section is removed, also remove unused CSS selectors, template variables, helpers, navigation builders, test markers, and stale docs references.
  12. Guard and verify: Update guard tests for the pattern, then run focused route tests, manage.py check, migration dry-run where relevant, Compose config check, git diff --check, and Playwright desktop/mobile layout verification.

Database Performance Checklist

Use this checklist when query-count tests, slow query logs, EXPLAIN, or repeated workloads show real cost. Do not apply every tactic blindly.

  • Add indexes after confirming frequent filter, join, or ordering fields such as account_id, device_id, user_id, status, or created_at. Avoid duplicate indexes.
  • Use select_related, prefetch_related, and filtered Prefetch objects for repeated relation access while keeping tenant/account scope identical.
  • Use grouped aggregates, .exists() for existence checks, and bulk count maps instead of counting inside loops.
  • Use .values() or .values_list() for read-only scalar/table payloads where model methods are not needed.
  • Use .only() or .defer() only after verifying serializers/templates will not touch deferred fields and create hidden follow-up queries.
  • Use bulk_create() or bulk_update() only when skipped save(), validation, signals, audit logging, and side effects are acceptable or handled elsewhere.
  • Use pagination, batching, or explicit limits for large lists. Do not load a full tenant hierarchy or report dataset unless the workflow requires it.
  • Cache repeated stable lookups through Django cache/Redis/Memcached only with a clear TTL and invalidation path. Cache keys must be backend-safe and must not expose secrets or personal data.
  • Keep transaction.atomic() around multi-write workflows that must stay consistent. Do not treat transactions as a query-count fix by themselves.
  • Use custom managers/querysets or raw SQL only where the ORM cannot express a complex query clearly, and add tests for tenant scope and result shape.
  • Use denormalized fields, database/materialized views, partitioning, or sharding only for proven high-volume bottlenecks after profiling, and document refresh behavior.
  • Use database constraints such as unique, check, and foreign keys to keep invariants in the database instead of relying only on Python-side validation.
  • Watch signal-heavy paths because per-row signals can erase bulk-operation gains or add hidden queries.
  • Profile with query-count tests, Django query logs, EXPLAIN, or APM before and after substantial optimization.
  • For async ORM/Channels work, optimize connection usage and concurrency only where the workload is truly concurrent.
