Layout migration playbook

SmartPole Layout Diagram

เอกสารนี้คือวิธีแก้ layout ให้ถูกทางก่อนลงมือแก้ production: อ่าน docs/html/*.html ของหน้าที่จะแก้, map ไป route/template จริง, ตรวจว่า data และเมนูสะท้อน workflow ที่มีประโยชน์ต่อการวิเคราะห์หรือไม่, แล้วค่อยแก้โดยใช้สี production และ header component เดิม.

North Star

เริ่มจาก docs ของหน้านั้น

เปิด docs/html/*.html เฉพาะหน้าที่กำลังจะแก้ เพื่ออ่าน order, grouping, class vocabulary, menu intent, และ analysis intent.

route และ data คือความจริง

เช็ก route/template/view/service จริงก่อนเสมอ. ข้อมูล, permission, package gate, form action, และ device/account scope ต้องมาจาก production.

คง shell เดิม

สีใช้ production theme เดิม, header ใช้ shared component ที่ทำไว้แล้ว, และห้าม copy fake rows, mock colors, CDN script, หรือ browser-side authorization.

Main Flow

1

เลือก slice เดียว

เลือก route เดียว เช่น /backoffice/energy/ หรือ /dashboard/. อย่าแก้หลายหน้าในรอบเดียวถ้าไม่ได้จำเป็น.

2

จับคู่ route จริง

ดู mapping ใน apps/core/tests/test_template_shell_guard.py แล้วเปิด route, template, CSS, JS, view, service, และ tests ที่เกี่ยวข้อง.

3

ตรวจ data และเมนู

ถามก่อนว่า data ที่จะแสดงสะท้อนเมนู/route นี้ไหม, ช่วยวิเคราะห์หรือจัดการงานจริงไหม, และมี backend owner หรือ permission gate ไหน.

4

แก้ layout แบบ minimal

ปรับ DOM order, wrappers, grid, spacing, reusable classes, และใช้ shared header component โดยคง route/form/query/action เดิมไว้.

5

ล็อก contract

เพิ่ม non-visible markers, static guards, route assertions, และ negative tests กัน mock-only blocks หลุดเข้า runtime.

6

ตรวจภาพและ tests

เช็ก desktop/mobile, no overlap, no fake data, focused tests, manage.py check, และ git diff --check.

Report / Export Concept

Report export ต้องเป็น purpose-first workflow: เลือก scope และวัตถุประสงค์การบริหารก่อน, ให้ Output Preview Table แสดง row set จริงจาก filters ปัจจุบัน, แล้ว export current preview เป็นไฟล์เดียวกัน.

1

เลือก scope

Platform Owner เลือก all, dealer subtree, หรือ customer. Dealer เลือก all customers ใต้ตัวเองหรือ customer เดียว. Customer เป็น fixed own account.

2

เลือก purpose

เลือกว่าจะ export เพื่ออะไร: operations overview, device operations, zone/map coverage, fault/maintenance, energy/carbon, package/license, หรือ raw payload diagnostics. ถ้าไม่เลือก ให้ default เป็น operations overview.

3

filter รายการ

ใช้ account scope, time range, และ search เป็น filter หลัก. Zone, tag, และ device set เป็น context columns ในตารางที่เกี่ยวข้อง ไม่ใช่ primary filter ซ้ำบนหน้า export.

4

Apply แล้วเห็น preview

Output Preview Table ต้องแสดง rows จริงจาก backend query หลัง scope/filter. ผู้ใช้ต้องตรวจข้อมูลบนหน้าก่อน export ได้.

5

Export current preview

Export ต้องหมายถึง preview ที่กำลังเห็นอยู่พร้อม filters เดิม. ห้ามโชว์ package/device/fault export buttons คู่ขนานจนทำให้คนไม่รู้ว่าจะได้ข้อมูลอะไร.

6

เลือก file type

หลังเห็น preview แล้ว export เป็นไฟล์ที่ต้องการ. Production Report Export ตอนนี้รองรับ CSV และ PDF จาก current filters.

Source of truth

Preview query และ export query ต้องใช้ scope/filter/purpose contract เดียวกัน. Export ไม่ควรมี hidden filter logic ที่ตารางไม่ได้สะท้อน.

Role behavior

Platform Owner/Dealer ใช้ AccountScopeService เพื่อ resolve visible tree/subtree/customer. Customer scope ต้อง fixed ที่ account ตัวเอง. Columns ต้องต่างกัน: Platform Owner เห็น Dealer + Customer, Dealer เห็น Customer, Customer ไม่ต้องเห็นทั้งสอง column เพราะเป็น own scope.

Regression guard

Template ต้องมี marker ว่า export is current-purpose/current-preview. Tests ต้องกันไม่ให้กลับไปเป็น three parallel export buttons หรือ raw payload default.

Map / Floor Plan Display Contract

/admin/accounts/account/<id>/change/ เป็นจุดเลือก Account.form_type ผ่าน field Map / floor. Field นี้เลือก renderer เท่านั้น: MAP ใช้ Leaflet/OSM และ FLOOR_PLAN ใช้ structured floor-plan renderer. ทั้งสอง mode ต้องแชร์ operational layer เดียวกันคือ customer/site scope, zone, tag, device id, device set/lot, marker state, selected device context, table, และ active issue rail. ห้ามตีความว่า MAP ไม่มี zone/tag หรือ FLOOR_PLAN เป็น workflow คนละระบบ.

0

Admin source

ใน Django admin ส่วน Customer / site profile ต้องเรียง Customer type, Map / floor, Customer size. customer_type เป็น business classification เท่านั้น ส่วน form_type = MAP | FLOOR_PLAN คือ source of truth สำหรับ renderer. ถ้าเป็น MAP ไม่ต้องมี building/floor; ถ้าเป็น FLOOR_PLAN จึงใช้ building/floor/position เพิ่มเติม.

1

Resolve scope

เริ่มจาก account/customer scope, zone, tag, device set/lot, connection, marker state, active issue, และ search ผ่าน backoffice_map_view. Platform Owner/Dealer เห็น visible tree; Customer เห็น own scope. Scope และ filters เป็นชุดเดียวกันทั้ง Map และ Floor plan.

2

Choose display mode

ผู้ใช้เลือก renderer: Geo Map หรือ Floor Plan. Production เปิดสองตัวนี้ก่อน; Satellite/Heat ต้อง gated จนกว่าจะมี source จริง. ถ้า form_type=MAP ให้ default เป็น Geo Map แต่ยังมี zone/tag/table. ถ้า form_type=FLOOR_PLAN ให้ default เป็น Floor Plan และเพิ่ม building/floor context.

3

Build shared payload

Backend สร้าง payload ชุดเดียวสำหรับ rows, zone/tag grouping, active alerts, selected device, device context drawer, และ state legend. Geo Map เพิ่ม lat/lng marker. Floor Plan เพิ่ม building/floor/position หรือ auto layout. Zone/tag/device ไม่แยก source ตาม renderer.

4

Render chosen canvas

Geo Map render ด้วย Leaflet/OpenStreetMap และไม่ require building/floor. Floor Plan render เป็น structured board จาก building/floor + zone/tag/device placement และไม่ require uploaded image. นอก canvas/table column ที่เกี่ยวกับ building/floor แล้ว action, issue, QR, และ state logic ต้องเหมือนกัน.

5

Sync context

คลิก marker, floor-plan node, alert rail item, หรือ table row ต้องเลือก device context เดียวกัน: center/highlight canvas, เปิด popup/drawer, QR, device detail, history, fault command center, หรือ work-order action ตาม permission.

6

Guard mutations

Filter และ mode switch ไม่ mutate placement. Drag/edit/save placement ต้องเป็น explicit action และต้องมี backend permission/service/test ก่อน. Read-only users เห็น map/floor/table แต่ไม่เห็น placement mutation controls.

Role columns

Platform Owner เห็น account scope เป็น dealer/customer tree และ table ต้องมี Dealer + Customer. Dealer เห็น customer scope ใต้ตัวเองและ table มี Customer เท่านั้น. Customer เป็น fixed own scope ไม่มี account selector และไม่มี Dealer/Customer columns.

Realtime rail layout

/map/ ใช้ component pattern เดียวกับ Dashboard Top Issues: workspace เป็น 12-column row, canvas = 9 และ realtime rail = 3 เมื่อเปิดอยู่. ถ้าผู้ใช้เลือก hide when clear ให้ canvas กลับเป็น 12; ถ้ามี active fault หรือ maintenance/work-order priority event ต้อง auto show rail อีกครั้ง.

Error vs feed

Realtime Error Rail แสดงเฉพาะ system-detected active issues จาก backend fault/alert state. Live Event Feed เป็น observability stream และให้ maintenance/work-order events ขึ้นก่อน; repair completed แสดงประมาณ 5 นาทีแล้วไปอยู่ใน work-order/fault history.

Map type tabs

Header ต้องมี Map, Satellite, Floor plan, Heat layer ตาม mock. Production เปิด Map และ Floor Plan ก่อน; Satellite/Heat ต้อง disabled หรือ gated จนกว่าจะมี tile/source/renderer จริง ห้ามใส่ fake renderer เพื่อให้เหมือน mock.

A

Building mode

เริ่มด้วย radio/segmented control ว่า account/site นี้เป็น single building หรือ multi building. Single building ใช้ default building อัตโนมัติ; multi building เปิด feature เพิ่ม building.

B

Create building

ถ้าเป็น multi building ให้สร้าง building ก่อน เช่น ชื่ออาคาร, site/account, optional description. Building เป็น container ของ floor ไม่ใช่ device scope โดยตรง.

C

Create floor

สร้าง floor ใต้ building หรือ default building เช่น Floor 1, Floor 2, Parking, Warehouse. Floor เป็น display/layout boundary ของ floor-plan mode.

D

Create zone

สร้าง zone ใต้ floor แล้ว add device id จาก scoped device list เหมือน map view. Device ที่อยู่ใน zone นี้จะเป็น candidate สำหรับ canvas/table/alert rail ของ floor นั้น.

E

Split tag

Tag เป็น subset ของ zone. ถ้าแยก tag ให้เลือกเฉพาะ device id ที่อยู่ใน zone นั้นเท่านั้น แล้วย้าย/assign device เข้า tag; ห้ามเลือก device นอก zone.

F

Show live lighting

View mode แสดง device light/node บน floor/zone board พร้อม flash/color ตาม legend เดียวกับ map: online-on, online-off, fault, offline, maintenance, disabled.

Admin / Frontend Rule
Admin source

Django admin Customer / site profile owns Customer type, Map / floor, and Customer size. Zone manager owns create/update/delete zone, create tag inside zone, and assign device with tag scoped to the selected zone.

Frontend reuse

/map/, /zones/control/, /map/?view=floor, and /zones/<zone_id>/floor-plan/ must use the same Zone + ZoneTag + Device.zone/tag contract. Renderer decides only canvas/position columns.

Current schema

MAP may leave Zone.building_name and Zone.floor_number blank. FLOOR_PLAN uses them for this production slice. Do not introduce Building/Floor tables until there is a separate lifecycle, permission, or reporting need.

Anti-pattern

Do not hide zone/tag when the renderer is MAP, do not let floor-plan tags select devices outside their zone, and do not make uploaded image availability decide whether floor-plan mode works.

Recommended production shape

Keep one /map/ workspace with view=map|floor|heat. Default view should come from Account.form_type when no explicit query is selected. Both Map and Floor mode use zone, optional tag, device set/lot, state, and issue filters. Floor mode additionally uses building and floor.

Floor plan prerequisite

Floor Plan mode needs building/floor structure only for its renderer. If the account is single building, create/use a default building. If multi building is selected, require building first, then floor, then zone and tag assignment. MAP mode does not need building/floor but still uses zone/tag.

Regression guard

Add markers for data-map-display-mode, data-map-floor-plan-canvas, data-building-mode, and shared selected-device context. Tests must verify floor mode does not require image upload and does not render the Leaflet-only canvas as the primary surface.

Zone Control landing rule: ถ้า Platform Owner/Dealer เปิด /zones/control/ โดยไม่มี customer_scope explicit ใน URL หรือ POST ห้ามใช้ persisted session scope เพื่อข้ามขั้นนี้ ต้องแสดง customer selector ก่อนเสมอ.

Scoped link rule: หลังเลือก customer แล้ว ปุ่มไป zone detail, floor plan, device list, map, และกลับ Zone Control ต้อง preserve customer_scope เพื่อไม่ทำให้ operator หลุดกลับไป selector ระหว่างทำงาน.

2

Choose building mode

ถ้า multi building เปิดอยู่ ให้มี step สร้าง/เลือก building. ถ้าไม่เปิด ให้ใช้ default/current building และไม่กินพื้นที่ด้วย building selector ที่ไม่มีประโยชน์.

3

Create floor

สร้าง floor/site area ภายใต้ building หรือ default building. Floor เป็น operational boundary สำหรับ floor-plan และ zone grouping.

4

Create zone

สร้าง zone ใต้ floor. Zone เป็น command/schedule/issue aggregation scope และเป็น source สำหรับ map/floor-plan context. Setup form ต้องเรียง field เป็น Building, Floor, Zone name, Description เพื่อให้ operator คิดจากสถานที่จริงลงมาหา control group.

5

Create tag

สร้าง tag เป็น subset ของ zone. Tag schedule/control ต้อง override zone ได้ตาม policy และห้ามเลือก device นอก zone.

6

Assign devices

แสดง device list/table ให้เลือก device id เข้า floor/zone/tag. ต้องแสดงจำนวน unassigned devices และสามารถ filter เฉพาะ device ที่ยังไม่ได้ assign ได้.

Single create entry: View mode แสดง hierarchy/readiness เท่านั้นและมีปุ่มเข้า setup/edit เพียงจุดเดียว. Zone / Tag Setup Tools ต้อง slide in เป็น drawer จากด้านขวา ไม่ใช่ section ยาวใต้หน้า. Drawer UX ต้องเรียงเป็น 1 Structure, 2 Zones / Tags. ห้ามมี global Create Tag แยกบนสุด เพราะ tag เป็น subset ของ zone และต้องจัดการใต้ zone card. Device assignment ต้องอยู่ในระดับ zone ก่อน: เลือก device id จาก unassigned pool เข้า zone. หลังจาก device อยู่ใน zone แล้วเท่านั้น จึงเลือก tag จาก tag ที่สร้างไว้ใต้ zone นั้นเพื่อผูก device เข้ากับ tag. Floor hierarchy ต้องใช้ floor-section + zone-node row ตาม mock. Quick control, schedule, และ tag schedule ต้องเปิดผ่าน operation drawer จาก row menu ไม่ใช่ panel ยาวที่กิน layout ใต้ hierarchy.

Required counters

Workspace ต้องบอกได้อย่างน้อย: buildings, floors, zones, tags, total devices, unassigned devices, online, fault, warning, scheduled groups. ตัวเลขต้องมาจาก resolved customer scope.

Hierarchy health

ต้องบอกได้ว่า issue อยู่ตรงไหนผ่าน floor-section และ zone-node เช่น Building A / Floor 2 / Zone Road B / Tags / Issues. Floor, zone, และ tag ควรแสดงสถานะ normal, warning, fault จาก device/fault rows ใต้ตัวเอง โดยไม่ต้องมี issue sidebar แยก.

Correct Edit Order

1. Read the target mock

อ่านเฉพาะ docs/html/*.html ที่ตรงกับหน้าที่จะแก้ แล้วแยกสิ่งที่เป็น layout intent ออกจาก mock data. อย่าเริ่มจาก CSS หรือ template โดยยังไม่รู้ว่า mock ต้องการ workflow อะไร.

2. Trace the production route

ตาม route ไปหา template, view, service/helper, context variables, permission gates, package gates, related CSS/JS, และ tests. ถ้า route ไม่ชัด ให้หยุด map ให้ชัดก่อน.

3. Check menu fit and analysis value

ข้อมูลที่จะเอามาแสดงต้องตอบหน้าที่ของเมนูนั้น เช่น dashboard ต้องช่วยดูภาพรวม, report ต้องช่วย export/analyze, device ต้องช่วย drill down/control. ถ้าไม่ช่วย workflow ให้เอาออกหรือ defer.

4. Preserve production shell

ใช้สี, token, sidebar, spacing base, และ white-label behavior เดิมของ production. Header ให้ใช้ templates/includes/frontend_dashboard_header.html หรือ component/shared pattern ที่มีอยู่แล้ว.

Filter Panel Contract

Production filter panels ต้องใช้ pattern เดียวกันทุกหน้า เว้นแต่มีเหตุผลเฉพาะของ workflow ที่ระบุไว้ใน template marker.

One filter group

ใช้ panel เดียวและ group เดียวชื่อ Filters สำหรับหน้าค้นหา/ตารางทั่วไป. Workspace setup ที่มี sequence ชัดเจน เช่น map mode หรือ zone building/floor/zone/tag อาจแยก group ตาม decision step ได้ แต่ต้องไม่ซ้อน card จนกินพื้นที่หรือทำให้ action ไม่ชัด.

One fields grid

ใส่ field ทั้งหมดใน responsive grid เดียว: scope/account, status/state, severity/type, search/date, และ action. Field ต้องใช้ min-width:0, width:100%, และ wrap ตาม container.

Apply only

Default action คือ Apply เท่านั้น. อย่าใส่ Reset/Clear ใน filter panel เว้นแต่หน้านั้นมี requirement ชัดเจนและไม่ทำให้ผู้ใช้เข้าใจผิดว่าข้อมูลถูกล้างจาก backend.

Decision Gates

copy structure

เอาเข้า production ได้

  • Section order and grouping
  • Menu-specific panels that improve analysis or operation
  • Grid vocabulary เช่น span-12, command panel, stat strip
  • Accessible labels and empty-state shape
  • Reusable card/menu/action patterns that map to real behavior
convert first

ต้องแปลงก่อน

  • Mock chart becomes empty or backend-driven chart shell
  • Static table row becomes queryset loop
  • Future action becomes disabled/hidden state until backend exists
  • Mock role/scope becomes account-scoped context
  • Mock navigation becomes an existing route or hidden until route exists
do not copy

ห้ามเอาเข้า

  • Fake customer names, fake devices, fake usage numbers
  • Mock-only buttons without server route or permission
  • Cards that do not help the menu's analysis or operation purpose
  • Raw provider secrets or internal payloads
  • Mock color/theme override that breaks white-label shell

Dashboard card menu

⋮ หลัง card actions ใช้สำหรับซ่อน widget card เท่านั้น. Contract คือ data-menu-contract="widget-card-hide-actions" และ restore ต้องอยู่ที่ hidden widget tray/library.

Audit table settings menu

⋮ หลัง 50 rows/page ใช้ตั้งค่าจำนวน rows ต่อหน้า. Contract คือ data-menu-contract="audit-table-page-size-settings" และต้อง preserve filter query เดิมเมื่อเปลี่ยนจำนวนแถว.

ถ้าจะดึงเป็น component กลาง ให้ share เฉพาะ visual affordance, focus state, popover shell, และ accessibility labels. Behavior ต้องเลือกจาก explicit contract/purpose ไม่ใช่จาก icon ⋮ อย่างเดียว.

Artifact Map

1. Docs source

docs/html/*.html ใช้เป็น spec. อัปเดต handoff เมื่อ behavior หรือ layout contract เปลี่ยน.

2. Production template

templates/**.html ต้องใช้ shared shell, route markers, real URL/forms, i18n, and permission gates.

3. CSS and JS

static/css/** และ static/js/** เก็บ layout behavior แยกจาก template logic.

4. Tests

test_template_shell_guard.py, test_static_asset_guard.py, route tests, and focused app tests lock the slice.

Rule for new docs files

ถ้าเป็น docs-only reference ให้เพิ่มชื่อไฟล์ใน DOCS_ONLY_SPECS. ถ้าเป็น runtime spec ต้องเพิ่ม mapping ใน ROADMAP_PAGES พร้อม production template ที่รับผิดชอบ.

Per-slice Checklist

Before edit

  1. เปิด docs source ของหน้าที่จะแก้ และ production template ข้างกัน.
  2. ระบุ route, view, CSS, JS, services, tests, permission gates, และ menu owner ที่เกี่ยวข้อง.
  3. เขียน section inventory: keep, convert, remove, defer พร้อมเหตุผลว่าช่วยวิเคราะห์หรือจัดการงานจริงไหม.
  4. เช็ก dirty worktree และอย่า revert งานอื่น.

During edit

  1. แก้ DOM order และ CSS ก่อน logic ใหม่.
  2. ใช้ shared header/component/pattern เดิมก่อนสร้าง component ใหม่.
  3. สีและ theme ต้องยึด production เดิม ไม่เอาสี mock มาครอบ.
  4. เพิ่ม non-visible markers เช่น data-layout-source.
  5. ห้าม hardcode mock values เพื่อให้หน้าดูเต็ม.

After edit

  1. เพิ่ม static guard และ route assertion ที่ตรงกับ contract ใหม่.
  2. เช็ก desktop/mobile ว่าไม่มี overlap, scroll trap, หรือปุ่มชนกัน.
  3. รัน focused tests, manage.py check, และ git diff --check.
  4. อัปเดต handoff หรือ canonical docs เฉพาะ behavior ที่เปลี่ยนจริง.

Definition of done

  1. Route ใช้ production data/scope/permission ครบ.
  2. ข้อมูลบนหน้าสะท้อนเมนูนั้นและมีประโยชน์ต่อ analysis/operation จริง.
  3. Header และ theme ใช้ component/token ฝั่ง production เดิม.
  4. Layout ใกล้ docs intent โดยไม่ copy mock-only data.
  5. Tests guard ทั้ง positive และ negative markers.
  6. มีบันทึกว่าอะไรทำแล้ว อะไร intentionally deferred.
