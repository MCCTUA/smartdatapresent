Implementation sequence

InfluxDB, API, package policy, device state engine, and new theme migration in one plan.

เอกสารนี้เป็นลำดับการแก้จริงสำหรับระบบ SmartPole เพื่อไม่ให้แก้แบบกระโดดไปมา: เริ่มจากฐานข้อมูลและ logic กลางก่อน แล้วค่อยย้าย UI จริงใน templates/* ให้ตรงกับ design spec ใน docs/html/*.html.

หลักที่ห้ามหลุด

  • UI ทุกหน้าอ่าน state ผ่าน API กลาง ไม่คำนวณ error เองคนละหน้า
  • InfluxDB เก็บ telemetry history, PostgreSQL เก็บ business/latest state
  • Package เป็นตัวกำหนด sampling, retention, visible range และ action lock
  • AccountScopeService + EntitlementPolicy ต้องคุมทุก query/action ก่อนส่งถึง UI
  • System issue, notification, work order และ maintenance ต้องมี lifecycle กลาง ไม่ปนกันในแต่ละหน้า
  • Header/theme ต้องเป็น include กลาง ไม่ซ้ำใน template รายหน้า
  • ทุกข้อความ UI/API/Telegram/report ต้องผ่าน translation key กลาง ไม่ hardcode English/Thai แยกหน้า
  • แก้ทีละ phase และตรวจ route/template หลังจบแต่ละชุด

1. Target Architecture

Final source of truth
Telemetry history InfluxDB

เก็บ voltage, current, power, energy, power factor, raw telemetry และ downsampled time-series ตาม package policy.

Business state PostgreSQL

เก็บ account, package, device latest state, issue, notification, command, maintenance, audit, report metadata.

API contract Django Ninja

เป็น gateway เดียวสำหรับ dashboard/map/device/fault/report. UI ห้าม query InfluxDB ตรง.

Realtime UI Channels + Redis

push latest state, issue changes, command status, notification badges และ live connection status.

3.1 Backend Contract Details

ต้องทำก่อนย้าย UI จริง
Input contract NormalizedTelemetryEvent

ทุก source เช่น MQTT, Node-RED, provider API, simulator, manual import ต้อง normalize เป็น schema เดียว มี account_id, device_id, event_id/correlation_id, timestamp, metric values, command reference และ source.

Idempotency Dedupe before write

worker/API ต้องตรวจ event_id หรือ source timestamp เพื่อไม่เขียน InfluxDB/PostgreSQL ซ้ำ โดยเฉพาะ gateway batch, retry, Node-RED replay และ late event.

Policy resolver PackageTelemetryPolicy

resolve จาก Account + PackageTier ก่อน ingest/query/export/control. คืน sampling interval, visible_from/until, retention, read_only, disabled_actions และ expiry_notice.

Scope gate AccountScopeService

Platform owner เห็น platform scope, dealer เห็น dealer + descendants, customer เห็นของตัวเอง. ทุก detail/mutation route ต้อง re-check scoped queryset ห้ามเชื่อ URL id อย่างเดียว.

Entitlement gate EntitlementService.runtime_access()

ทุก API ต้อง clamp requested_time_range ด้วย visible_until และคืน mutation_allowed/blocked_reason. Control/schedule/report export/generation paths block through this serviceแล้ว; current dashboard historical/generic line-chart APIs clamp แล้ว. InfluxDB query adapter ต้อง reuse policy นี้เมื่อทำจริง. UI แสดงตามผลจาก backend เท่านั้น ไม่เดาเองว่า action ไหนควร disable.

State ownership DeviceLatestState + ActiveIssue

หน้า dashboard/map/device/fault/notification ต้องอ่านสถานะเดียวกันจาก backend state. ห้ามให้แต่ละหน้า infer fault จาก raw telemetry เอง.

4. Package Logic That Must Be Implemented

Package controls data access

Telemetry interval

package กำหนดว่า customer นี้เก็บค่า telemetry ทุกกี่วินาที/นาที เช่น 1s, 5s, 1m, 15m. Ingest pipeline ต้อง resolve policy จาก device/account/package ก่อนเขียนลง InfluxDB.

Software expiry

ถ้า software package หมดอายุ ระบบยังรับ data จาก API/MQTT ต่อ แต่ UI แสดง history ได้ถึง package_end_date เท่านั้น. Alerts ยังเห็นได้แบบ read-only แต่ control/repair action/export beyond package ต้อง lock.

Hardware expiry

ถ้า hardware/โคมไฟใกล้หมดอายุหรือหมดอายุ ต้องสร้าง warning/notification/maintenance risk. ไม่ควร block data ingest แต่ต้องแสดงสถานะชัดใน dashboard, map, device, faults, reports.

Renewal rule

เมื่อต่ออายุ package แล้ว API visible range ต้องขยายต่อจากวันที่ต่ออายุ/วันที่ package ใหม่มีผล. ข้อมูลที่ ingest ไว้หลังวันหมดอายุไม่หาย เพราะอยู่ใน InfluxDB อยู่แล้ว แต่ UI จะ unlock ให้เห็นตาม policy ใหม่.

Telegram bot ต้องทำแค่รับข้อความ, resolve user binding, และส่งคำถามเข้า query gateway. Gateway ต้องเรียก McpQueryPolicy, CapabilityResolver, account scope, usage quota, และ MCP tool allowlist ก่อนสร้างคำตอบ. ถ้า package หมดอายุ ให้ตอบได้เฉพาะ read-only ตาม visible_until และห้าม ack/repair/export/control ผ่าน Telegram.

Package admin impact

หน้า Package Tier admin เพิ่ม ai_mcp_query_enabled, ai_mcp_query_limit_per_month, และ ai_mcp_allowed_tools แล้ว โดยแยกจาก notification delivery ปกติ เพราะ “รับ Telegram alert” กับ “ถามข้อมูลผ่าน Telegram + MCP” เป็นคนละ feature และคิด quota คนละแบบ.

4.2 Issue vs Maintenance Workflow

แยก system issue กับ manual maintenance

System-detected issue flow

  • Issue Rule Engine สร้าง issue จาก telemetry/command/offline/anomaly เท่านั้น
  • Operator หรือผู้มีสิทธิ์กด acknowledge เพื่อรับทราบจาก dashboard/faults/notifications
  • Manager/admin หรือผู้มีสิทธิ์ assign เจ้าหน้าที่หรือสร้าง work order
  • Technician/assignee บันทึก problem master data, note, repair action, completed_at
  • ระบบ re-check telemetry หลังซ่อม ถ้าปกติจึง close/resolved ได้ตาม policy

Manual / preventive maintenance flow

  • ไม่แสดงใน dashboard Top Issues หรือ issue-only rail ถ้าไม่ได้ผูกกับ system issue
  • เริ่มจาก device detail, faults maintenance records, หรือ planned maintenance workflow
  • ใช้ work order/maintenance record แยกจาก ActiveIssue แต่ยัง link device/account/zone ได้
  • ถ้า software expired: ดูข้อมูลได้แบบ read-only แต่ create/assign/repair/close ถูก lock
  • hardware/lamp expired เป็น warning และ recommendation ไม่ใช่ตัว cap telemetry visibility

4.3 Notification Config + Telegram Setup

API value -> rule -> alert -> route -> Telegram

Gap ที่ต้องแก้ใน implementation plan

การรับค่า telemetry จาก API/MQTT ยังไม่พอ ต้องมีหน้า config/rule เพื่อกำหนด threshold, severity, routing, recipient, channel readiness และ Telegram binding. ถ้าไม่มีส่วนนี้ ระบบอาจสร้าง issue ได้แต่ไม่ส่งแจ้งเตือน หรือส่งผิดคน/ผิด channel.

Rule config Fault / Alert thresholds

ตั้งค่า event_type, metric, operator, threshold, debounce window, severity, duplicate window และ suppress rule เช่น lamp_state_unconfirmed, promoted lamp-state fault, voltage sag, offline timeout. Provider command accepted ต้องเข้า pending verification ก่อน แล้วจึง promote เป็น FaultOccurrence/AlertEvent เฉพาะเมื่อยังไม่ confirmed หลัง debounce.

Channel config Telegram bot/webhook

ใช้ AccountNotificationChannelConfig ตั้ง Telegram platform default หรือ account-owned bot token, webhook secret และ verified status.

Recipient config Add / link Telegram user

ใช้ NotificationChannelBinding หรือ link-code flow เพื่อผูก account user กับ Telegram chat_id. User preference ต้องเปิด Telegram และ severity ที่ต้องการรับ.

Routing config Who gets what

ใช้ NotificationRoutingPolicy กำหนด critical/warning/info, event_type, channel_order, role, capability, specific users, timetable/digest/mute.

Recovery config Recovered messages

customer เลือกได้ว่าจะรับ Telegram เมื่อ device/network กลับมาใช้งานปกติหรือไม่. ค่า default ควรเป็นปิดหรือเปิดตาม package/customer policy ที่กำหนดชัดเจน.

Device issue notification scope rule

เมื่อ issue เกิดจาก device_id ระบบต้อง resolve เจ้าของจริงก่อน: device_id -> device.account_id/customer -> parent dealer chain -> platform owner. ค่า payload_json.account_id หรือ fault_occurrence.device.account_id ต้องเป็น customer เจ้าของ device. Default recipient scope คือ customer account นั้นเท่านั้น. Dealer หรือ Platform Owner จะได้รับ message เฉพาะเมื่อมี policy/option opt-in สำหรับรับ alert จาก child/customer scope.

Purchase lot inventory/commercial/entitlement source DeviceSet / customer purchase lot in account device workspace Lot คุมจำนวนอุปกรณ์, pricing line, import/export, purchase date, software/hardware expiry. Lot ไม่ใช่ zone และไม่ใช่ตำแหน่ง.
Floor / site area บอกชั้น อาคาร หรือพื้นที่สำหรับ floor plan Zone fields เดิมมี floor_number, building_name, floor_plan_meta; target อาจแยก FloorPlan/FloorArea ใช้เฉพาะ renderer แบบ FLOOR_PLAN. MAP ไม่ต้องมี building/floor แต่ยังต้องมี zone/tag ได้. ถ้า FLOOR_PLAN ยังไม่มี x/y ให้ใช้ auto layout ได้.
Zone operational grouping สำหรับ control, schedule, issue, report Zone, ZoneDevice Zone เป็น shared operational layer ทั้ง MAP และ FLOOR_PLAN. ใน MAP อาจเป็น geographic/logical zone; ใน FLOOR_PLAN อาจผูก floor/building เพิ่ม. ห้ามใช้ zone แทน lot.
Tag filter/group ย่อย เช่น road, machine line, pole group Zone/tag model or target tag relation Tag เป็น subset ของ Zone และใช้เหมือนกันทั้ง MAP/FLOOR_PLAN เพื่อ filter, compare, report, schedule, และ action scope. ไม่ควรเป็น source หลักของ entitlement.
Device placement ตำแหน่งแสดงผลบน map/floor plan MAP: lat/lng. FLOOR_PLAN: optional x/y, otherwise auto layout. ถ้าไม่มี x/y ให้เรียงแบบ Floor -> Zone -> Device ID สำหรับ operator หรือ Floor -> Zone -> Lot -> Device ID สำหรับ inventory review.
Creation flow Customer -> package -> lot -> device -> placement

สร้าง customer แล้วเลือก package. จากนั้นสร้าง purchase lot ตาม pricing/package line, import/add devices เข้า lot, แล้วค่อย assign floor/site, zone, tag และ placement.

MAP flow lat/lng first

ใช้ตำแหน่งจริงจาก provider/manual drag. ไม่มี requirement เรื่อง building/floor แต่ยังต้องแสดงและ filter ด้วย zone/tag เหมือนเดิม. Lot แสดงเป็น inventory badge/filter เท่านั้น.

FLOOR_PLAN flow floor/zone first, x/y optional

เพิ่ม building/floor/area context สำหรับ renderer. Zone/tag/device/action logic ยังเหมือน MAP. ถ้ามี uploaded/generated floor plan ให้ place device บน x/y; ถ้ายังไม่มีตำแหน่ง ให้ renderer auto layout ตาม floor, zone, lot และ device id.

10. Validation Checklist

ตรวจหลังจบแต่ละ phase

Technical checks

  • docker compose config --quiet ต้องผ่านหลังเพิ่ม InfluxDB
  • settings/import compile ต้องผ่านหลังเพิ่ม config
  • API ต้อง apply tenant/account scope ทุก endpoint
  • InfluxDB query ต้องถูกจำกัดด้วย package visible range
  • Telemetry ingest ต้องมี idempotency/dedupe test
  • State engine ต้องไม่สร้าง duplicate active issue ทุก telemetry point
  • Scope/permission tests ต้องกัน dealer/customer ข้าม account
  • Notification rule/routing tests ต้องยืนยันว่า critical issue ส่ง Telegram ได้จริงเมื่อ config พร้อม
  • Notification scope tests ต้องยืนยันว่า device issue ส่งให้ customer เจ้าของ device และ parent dealer/platform เฉพาะ opt-in เท่านั้น
  • Recovered notification tests ต้องยืนยันว่า network/device กลับมาปกติแล้วส่ง Telegram เฉพาะ customer ที่เปิด option
  • Maintenance notification tests ต้องยืนยันว่า created/updated/completed event ส่งตาม routing option และแสดง UI state ถูกต้อง
  • Telegram token/webhook secret ต้องเข้ารหัสและไม่ render กลับใน HTML/API
  • Telegram MCP/AI query tests ต้องยืนยันว่า package ที่ไม่เปิด feature ตอบว่า blocked by package entitlement
  • AI query quota tests ต้องยืนยันว่าเกิน daily/monthly limit แล้วไม่เรียก MCP และบันทึก denial audit
  • AI query expiry tests ต้องยืนยันว่า software expired แล้วตอบได้เฉพาะ read-only ใน visible range และห้าม ack/repair/export/control
  • AI query scope tests ต้องยืนยันว่า customer/dealer/platform owner ถามได้เฉพาะข้อมูลใน scope ของตัวเอง
  • Translation tests ต้องยืนยันว่า UI/API/Telegram/report ใช้ key เดียวกัน และ fallback th -> en หรือ locale ที่กำหนดไม่ทำให้ UI พัง
  • API error tests ต้องยืนยันว่า response มี stable code และ message_key ไม่ให้ frontend parse English string
  • Recipient resolver ต้อง block user ที่ไม่มี preference, capability, binding, quota หรืออยู่ใน quiet hours
  • Channels ต้องส่งเฉพาะ event สำคัญ ไม่ stream raw telemetry ทั้งหมด
  • Export ต้องมี preview table และ audit log

UI checks

  • ไม่มีหน้าไหนหลุดเป็น old header/theme ใน scope ที่ migrate แล้ว
  • ทุกหน้าที่มี device click ต้องเปิด shared device QR/detail popup/drawer ได้
  • Issue state ต้องสอดคล้องกันใน dashboard/map/device/fault/notification
  • MAP และ FLOOR_PLAN ต้องเลือกจาก layout mode/form_type ไม่ใช่เดาจาก customer_type
  • Floor plan mode ต้อง render ได้แม้ยังไม่มี x/y โดยใช้ auto layout ตาม floor/zone/lot/device id
  • Purchase lot ต้องแสดงเป็น inventory/package/expiry context แต่ไม่ถูกใช้แทน zone/floor/tag
  • Responsive grid ต้องไม่มีพื้นที่ว่างใหญ่หรือ card ทับกัน
  • Dark/light theme ต้องใช้ token กลาง ไม่ override รายหน้า
  • Vertical ellipsis card menu ใช้เก็บ export/config/hide/report action ที่รก
  • ภาษาใน header, filter, card, drawer, table, export menu, empty state และ validation message ต้องเปลี่ยนตาม selected locale
