กล่อง flow สำหรับเพิ่ม lot, เพิ่ม device id/pole id, เลือก location type, และการแสดงผล dashboard โดยอิงเอกสารแม่กับ logic ใน service/form/view จริง.

แกนคิดเดียว

Device identity, placement, telemetry, package entitlement, and reports must all pass through shared services. ห้ามให้หน้า admin/frontend/report สร้าง logic ซ้ำ เพราะจะเกิด drift ทันทีเมื่อ device ย้าย customer, lot หมดอายุ, หรือ Pole Group ใช้ zone/tag เป็น Group/Pole.

Box Diagram — Add Lot → Add ID → Location → Dashboard

Logic surface map: source of truth = DeviceSet, DeviceSetPricingLine, Device, DeviceLotService, CustomerDeviceAdminForm, node_placement_policy.py, and serialize_device_summary(). Management surfaces = DeviceSet admin, account manage devices, CSV import. Display surfaces = device-list, map, dashboard, device detail, reports.

Lane A — Create / Manage Lot

A1 · Select customer scope

PO/Dealer เลือก customer ก่อนสร้าง lot; Customer เห็น workspace ตัวเองเท่านั้น. ทุก query ต้องผ่าน account scope helper.

A2 · Create DeviceSet lot

/admin/smartpoleapp/deviceset/ กำหนด package/trial, lifecycle dates, software/hardware expiry, fetch policy.

A3 · Choose lot_kind + layout

Lamp IOT = telemetry/control. Pole Group = manual pole items; group meter/fault API เป็น Phase 2. Layout = Map หรือ Floor.

A4 · Add pricing lines

DeviceSetPricingLine เก็บ bucket เช่น 100W x 10, 200W x 20. Quantity ที่ซื้ออยู่ที่ lamp_quantity.

A5 · Summary / capacity SSOT

DeviceLotService.lot_summary() และ can_add_device_to_line() คำนวณ used/remaining/status/warning ให้ admin/frontend เรียกชุดเดียว.

Lane B — Add Device ID / Pole ID

B1 · Open Manage devices

/admin/accounts/account/<id>/devices/ โหลด lot summaries, pricing filters, add-device drawer, import/template/export ต่อ lot.

B2 · Pick pricing detail

เลือก line ที่จะ consume slot. ถ้า line เต็มหรือ lot expired/inactive form จะ reject ผ่าน clean_pricing_line().

B3 · Field rules by lot_kind

Lamp IOT ต้องมี id, watt, IMEI/SIM expiry, serial, catalog. Pole Group ต้องมี pole id + watt; ไม่มี SIM/serial/catalog.

B4 · Generate QR round 1

ก่อน save ต้อง generate QR. QR bind กับ URL device_qr_detail จาก device/pole id; Pole Group ไม่มี serial ก็ยังมี QR.

B5 · Save + bind lot

save ตั้ง account, device_set, pricing_line. Lamp IOT bootstrap provider; Pole Group skip provider sync.

Lane C — Location Type / Placement

C1 · Entry point

/device-list/ Location column เปิด placement drawer. /devices/<id>/ เป็น read detail ไม่ใช่ placement editor.

C2 · Place later

สร้าง id/pole ได้ก่อนโดยยังไม่วางตำแหน่ง. ระบบยังถือว่าไม่สมบูรณ์จนบันทึก placement และ re-stamp QR รอบสอง.

C3 · Map placement

เก็บ latitude + longitude; form clear position_x/y_pct. Map marker แสดงเมื่อมี lat/lng.

C4 · Floor placement

เก็บ zone + position_x_pct/position_y_pct; form clear lat/lng. Floor plan บังคับ zone.

C5 · Pole Group rule

Contract target: ใช้งานจริงต้องมี Zone=Group และ Tag=Pole ตอน placement/import. Live code ตอนนี้บังคับ zone แต่ tag_required() ยังบังคับเฉพาะ group/meter node; ต้องแก้ policy/test ให้ตรง contract.

Lane D — Dashboard / Map / Report Display

D1 · Serialize device

serialize_device_summary() คืน placement status, location source, lat/lng, zone/tag, lot fields ให้ device-list/map/dashboard ใช้.

D2 · Conditional display

DeviceLotService.scope_display_flags() ตัดสิน SIM/control/zone/type columns จาก lot_kind/layout จริงใน scope. ห้าม template คำนวณเอง.

D3 · Dashboard metrics

dashboard scoped queryset → filters → live snapshot refresh → IoTDashboardAggregationService → history chart/analytics.

D4 · Dashboard map

dashboard map payload plot เฉพาะ device ที่มี lat/lng และจำกัด 100 markers; floor-only devices ต้องดูผ่าน floor/zone workspace.

D5 · Reports / exports

Report/export ต้องใช้ current preview query/filter เดียวกับ UI และ clamp date window ตาม package expiry ก่อน query/export.

SmartPole SSOT Flow Account scoped · Lot typed · Owner stamped · Service-first · Guarded by tests

1. Account / Tenant

  • Platform Owner → Dealer → Customer → User
  • ทุก query ต้องผ่าน account context/helper
  • Branding, package, permission, visibility แยกตาม account tree

2. Package / Lot

  • DeviceSet = lot purchase + lifecycle
  • DeviceSetPricingLine = quantity/watt/price bucket
  • DeviceLotService = summary/capacity/status SSOT

3. Device Provision

  • PO/Dealer สร้าง identity ก่อน placement ได้
  • QR รอบแรกหลัง save identity/provision data
  • ห้ามสร้าง device เกิน lot capacity

4. Placement

  • Map = lat/lng
  • Floor = building/floor/zone/tag/x/y
  • Pole Group ใช้งานจริงต้องมี Zone=Group, Tag=Pole

5. Telemetry Ingest

  • Device → EMQX → Node-RED/consumer → Django API/service
  • PostgreSQL = business state/latest/fault
  • InfluxDB = historical telemetry, owner-safe tag account_id

6. Fault / Control

  • Control target = current assignment + permission + entitlement
  • Fault rows must stamp account at write time
  • Pole Group fault uses expected watt vs measured group watt

7. UI / API / Reports

  • Dashboard, device list, map, zone, report read shared payloads
  • Exports must use same filtered preview query
  • Expiry/date windows must clamp before query/export

8. Runtime Decision

  • Python target = 3.13
  • Django 6.0 supports Python 3.13
  • Upgrade slice: Dockerfile, pyproject, lock, requirements, CI

9. InfluxDB Decision

  • Production-safe path now = keep InfluxDB 2.7
  • Reason: v3 Core is not drop-in for Flux/history workload
  • Future: rewrite adapter to SQL/InfluxQL before v3 cutover

Flow By Responsibility

Write Path

All writes must go through services that validate scope, package, capacity, and ownership.

  • Account create/update → account services
  • Device import/add → DeviceImportService + DeviceLotService
  • Telemetry write → ingestion + owner stamp

Read Path

Historical reads must not trust the device current account after transfer.

  • Current owner → DeviceOwnershipService.current_owner()
  • Historical owner → stamped account_id
  • Package/lot display → account_lot_summary()

Guard Path

Every repeated rule needs a test that fails when a surface bypasses the SSOT.

  • No duplicated map payload logic
  • No cross-customer mutation on active device row
  • No v3 Influx cutover before adapter rewrite

Implementation Order

  1. Keep InfluxDB 2.7 in compose and docs as current runtime decision.
  2. Upgrade Python to 3.13: Dockerfile, pyproject, uv.lock, requirements, GitHub workflows.
  3. Keep telemetry flags conservative: Influx write/query off until tests confirm behavior.
  4. Refactor only through InfluxTelemetryService when preparing v3; no dashboard/report direct query.
  5. When v3 is revisited, write SQL/InfluxQL adapter tests first, then compose change, then staged dual-run.
